Problem statement

Musanze Safe Markets is running a one-day pilot. A field officer must see the assigned market zones, record one fictional vendor inspection, and attach one evidence photo. There is no server. Names and phone numbers in the demo are fictional. The record lives only in the phone’s memory for this session.

Target field officer

Primary user: a market field officer walking between stalls with one hand free, often in bright sun, using Expo Go on an Android phone. They are not a designer. They need the next step to be obvious, errors to say what to fix, and the group code visible so the assessor can confirm the right build.

What this document owns

Member 1 defines the scenario, the task flow, the route map, the wireframes, the visual system, and the accessibility rules. Members 2, 3, and 4 implement those rules. The built app must match this document.

Page 2 · User and task flow

2. User and task flow

Primary user. Field officer on the Musanze Safe Markets pilot.

Goal. Register one fictional stall inspection and keep it in an in-memory list that can be opened again from Records.

Constraints. Expo Go on Android. No backend, database, API key, or real personal data. Larger system font and a narrow screen must stay usable. Invalid input must not reach the saved list.

Happy path

1. Open app. Read group code in the header.
→
2. Home shows six stalls. Officer checks name, status, priority.
→
3. New Inspection. Fill alias, stall code, category, phone, risk, consent.
→
4. Capture or pick one photo. Preview it.
→
5. Review shows fields, photo, time, group code.
→
6. Save. Records lists it. Details opens it. Back keeps the list.

Alternate paths the assessor will try

  • Empty catalog. The officer types a search that matches nothing. The list is replaced by an empty state with a way to clear the search.
  • Invalid form. Blank fields, a stall code that breaks the pattern, a phone that is not a fictional Rwanda mobile number, or missing consent. Each fault shows a message under that field. Review does not open.
  • Permission denied. The camera or gallery permission is refused. The form stays. A short message explains what happened and offers Try again. The other source (camera or gallery) remains available.
  • Picker cancelled. The officer backs out of the camera or gallery. Message: “No image selected. You can try again.” Nothing else is cleared.
  • Replace or remove. After a preview, Replace opens the source again. Remove clears the preview and blocks Review until a new image is attached.
  • Back. From Details, back returns to Records with the same in-memory list. Switching tabs does not wipe the form or the saved records.

Inspection the officer types

  • Vendor alias — required, at least 2 characters. Example: Mama Keza.
  • Stall code — required, exact pattern MZ-[A-F]-NNN. Example: MZ-A-014. Letters A to F only. Three digits.
  • Category — required, one of Produce, Grains, Meat, Clothing, Household, Cooked food.
  • Contact number — required, fictional Rwanda mobile: +250 7XX XXX XXX. Example: +250 788 123 456.
  • Risk level — required, Low, Medium, or High.
  • Consent — required checkbox: “I confirm this record uses fictional demo data only.”
  • Evidence image — required before Review. One photo from the camera or the gallery.

On Save, the app adds an id and an ISO timestamp and appends the record to the in-memory list. Leaving the app may clear that list. That limit is acceptable for this assignment.

Page 8 · Accessibility and design decisions

8. Accessibility and three decisions

  • Contrast. Body text #1A1A1A on #FFFFFF and on #F4F1EA. Primary button is white on #1B4D3E. Error text #9B2335 is also paired with the words of the message.
  • Touch targets. Buttons, tabs, cards, and the consent row are at least 48 by 48.
  • Font scale. Layout is Flexbox with wrapping text. No clipped single-line chips. The assessor will enlarge the device font.
  • Errors. Each message names the field and the expected pattern. Example: “Stall code must look like MZ-A-014.”
  • Not colour alone. Status chips include the word Open, Pending, Flagged, or Closed.

Decision 1 — Search is how the empty state appears

The pilot always has six assigned stalls, so a permanently empty home would be false. A search box lets the officer narrow the list and lets the assessor reach a real empty state. Clear search puts the six stalls back. Justified because test 2 asks for six records and an empty state in the same catalog.

Decision 2 — The photo is required before Review

The scenario says the officer documents the stall with one evidence image, and the review screen must show that image. The form therefore blocks Review until a preview exists. Permission denial and cancellation stay on the form with a recovery message, so a refused camera does not trap the officer: they can try again or use the gallery.

Decision 3 — One exact stall-code pattern, shown on the field

The brief asks for an exact stall code pattern but does not print one. The product uses MZ-[A-F]-NNN so every zone letter in the catalog (A through F) can match a stall, and the officer can see a correct example under the field. The same pattern is what Member 3 validates. Unseen wrong codes such as A14, mz-a-14, or MZ-G-001 fail.
